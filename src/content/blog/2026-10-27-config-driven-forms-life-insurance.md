> 這篇是我到人壽專案第一週的心得。專案細節不方便講，客戶和內部工具都不會出現名字；業界的部分是我查資料整理的，來源放在文末。

先講結論：在人壽的專案裡，我寫的主要不是畫面，是設定檔。

我做前端好幾年，Vue 寫了很多後台。到職第一週被分到「其他文件」，五份保險文件：一份批註書、兩份同意書、一份申請書、一份約定書。我以為又是刻表單，結果打開專案才發現，幾乎不用寫元件。

每一張表單，就是三份 JSON：

- **欄位**：有哪些格子、是單選還是勾選、選項代碼是什麼。
- **排版**：格子放在哪張卡片、排成幾欄。
- **規則**：什麼時候要跳錯誤訊息、什麼時候要停用某一格。

公司有一套表單引擎，吃這三份設定就把畫面畫出來。我這週的工作，大部分是把需求文件翻譯成這三份 JSON。

一開始我覺得很怪，同事說後端為主的專案常這樣，人壽跟銀行尤其多。我去查了一下，發現這不是單一專案的習慣，是這個產業的長相。

## 保險業本來就是「設定優先」

查了才知道，保險的核心系統早就是這樣設計。

Duck Creek 是做保險核心系統的大廠，他們有一篇文章直接把 low code 講成一種設計原則，不是某個功能。商品、費率、規則、流程用設定改，底層程式盡量不動。他們列的理由我看了很有感：法規一改，不用半夜緊急上版；設定是看得到、查得到的，主管機關問「誰改了什麼、為什麼改」，答得出來。

另一家 Socotra 更直接，他們的 UI SDK 說表單是從資料模型動態產生的，不是一個商品刻一次。商品一變，畫面就跟著變。

Forrester 在 2024 年也出過一份報告，專門講金融和保險業的 low code。摘要裡提到一個很實際的原因：這兩個產業非常依賴軟體，但工程師很難找。

這些放回我的專案，就很好懂了。

---

## 為什麼人壽特別需要這樣做

### 表單多，而且一直變

一張保單背後有要保書、各種同意書、告知書、批註書、申請書。我這週五份只是「其他文件」裡的一小角。

而且這些文件會變。今年四月，金管會才修了投保和電訪相關的規定，像是關懷提問可以改用視訊，聯絡不上可以改發簡訊、Email、App 推播。規定一動，流程和表單就要跟著動。

如果每張表單都是手刻的 Vue 元件，每一次法規調整都是一次改版。寫成設定檔的話，很多時候改的是一行 JSON。

### 文件就是規格

這是我第一週最大的震撼。

我遇到一題寫著「請擇一勾選」，需求文件給的元件卻是複選框。我的直覺是改成單選，一行設定的事。

結果不能改。人壽專案的字詞、元件、選項都要照文件做。文件背後是條款和客戶簽過名的紙本，畫面跟紙本對不起來就是風險。而且單選跟複選存進系統的資料格式不一樣，前端自己改，後端就對不上了。

設定檔在這裡有一個好處：它跟需求文件幾乎是一對一。一個欄位對到文件的一列，一條規則對到文件的一列。哪一列做了、哪一列還沒做、為什麼沒做，都可以逐筆追。

我後來的做法是：照文件做出來，覺得怪的地方寫成問題，帶去問能拍板的人。看到問題不是錯，自己決定答案才是。

![窗仔手上拿著橡皮擦想改掉需求文件上的字，旁邊一個寫著「照文件」的牌子把他擋住；他改成拿便條紙寫下問號](/blog/2026-10-27-config-driven-forms-life-insurance/02-follow-the-document.png)

### 同一套邏輯，要跑在很多地方

我們的專案有 App，也有 Web。同一個判斷，App 在裝置上跑，Web 透過 API 跑，讀設定的方式不同，但規則是同一份。

規則寫成資料，而不是寫死在某一端的程式裡，才有辦法讓不同的端共用。

## 那前端在做什麼？

這是我一開始最困惑的地方：不寫元件，那我在幹嘛？

做了一週，我覺得前端的工作沒有變少，是換了位置。

**讀懂需求文件。** 一份申請書可能有二十個欄位、四十幾條規則。每條規則要判斷：元件屬性就做得到嗎？能重用既有的規則嗎？還是要新增？還是根本要等資料？我其中一份文件有 48 條規則，最後 38 條列成「待確認」，因為它們需要的資料，API 還沒開始做。

**分清楚現在能做什麼。** API 還沒有的時候，我只做「只用到這張表單自己欄位」的規則，像是必填、兩欄互相必填、不安全文字檢核。需要主約幣別、案件狀態的規則，一律不拿假資料去湊。假資料會讓規則「看起來能跑」，上線時就變成沒人記得的坑。

**驗證到真的會顯示。** 有一次我在四個欄位綁了文字檢核，測試下去，兩個欄位就是不跳錯誤。查了才知道，那兩格依規定一打開就是停用的，表單核心不會檢核停用的欄位。JSON 有寫、規則有綁，都不代表使用者看得到。

**記錄差異。** 需求文件之間也會打架。同一張表單的標題，盤點表說在第一張卡片，畫面結構說在第二張。先跟主管定好以哪一份為準，之後每次衝突照同一條規則處理，差異寫進說明文件。

## 這種做法的代價

設定檔驅動不是沒有缺點，我第一週就撞到幾個。

**元件做不到，就真的做不到。** 有一題的選項我想讓它靠左，結果單選元件沒有對齊的屬性。最後是把它塞進三欄排版的第一欄，用欄寬把選項擠到左邊。團隊的規範也很清楚：不准自己寫 CSS 覆寫、不准自製元件，做不到就記下來，等表單引擎補上。

**多了一層，除錯也多一層。** 畫面不對的時候，要分清楚是設定寫錯、引擎的預設行為、還是規則的觸發時機。我有一次被建置腳本坑到：它用需求文件把畫面結構覆寫掉，結果兩張卡片顯示同一個標題。

**有些事 schema 表達不了。** LogRocket 今年有一篇談 schema 驅動表單的文章，提到需要打資料庫的非同步驗證，還是得另外接。我們也一樣，頁面層級的提示（例如離開頁面前提醒你還沒勾），目前就沒有地方可以設定。

**前端的成就感來源變了。** 以前做完一個漂亮的互動很有感，現在做完是一份 JSON 加一份逐筆對照的紀錄。成就感比較像「這張表單的每一列需求，我都說得出去向」。

---

## 第一次做人壽，我學到的

做了一週，我覺得這種開發方式跟產業的性質是綁在一起的。

保險跟銀行的東西，正確比好看重要，可追溯比快重要。法規會變、文件會變、同一套規則要跑在好幾個地方。把畫面跟規則寫成設定，是把「會一直變的東西」跟「不該亂動的程式」分開。

對前端來說，這不是被降級成寫 JSON 的人。比較像是從「刻畫面的人」變成「把需求翻譯成系統看得懂的格式，並且說得出每一個決定從哪裡來的人」。

我還在適應，不過已經開始覺得，這種專案裡最值錢的前端能力，可能不是手速，是讀文件、問對問題，還有知道什麼時候不要自己改。
