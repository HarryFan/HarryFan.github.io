> 這篇是在人壽專案用了兩週表單套件之後的整理。客戶、公司和內部工具都不會出現名字，文中的規則名稱與設定都是我改寫的示意，不是專案原文；業界的部分是查資料整理的，來源放在文末。

先講結論：**壽險業的 UI Kit，賣的不是元件，是「契約」。**

今年找工作的時候，我面試過一個前端主任的職缺，工作內容寫「建立公司的 UI Kit」。那時候我腦中的 UI Kit，是一套按鈕、輸入框、卡片，加上 Storybook 和設計 token。面試沒上，我也一直沒想通保險公司要的 UI Kit 跟一般的差在哪。

後來到人壽的行動投保專案，`package.json` 裡有一行：

```json
"<表單套件>": "file:<表單套件>-1.0.0.tgz"
```

這兩週我每天都在跟這個套件打交道：寫設定、撞到它做不到的地方、寫擴充、記錄限制。用久了才發現，它正好回答了我面試時沒想通的問題。

我是使用端，看不到套件的原始碼和設計討論。下面是我從「怎麼被要求使用它」反推回來的設計，跟我自己的心得。

![窗仔站在一個寫著「UI Kit」的大箱子前，打開後裡面不是一排按鈕，而是四份文件：欄位、排版、規則、文字](/blog/2026-11-05-life-insurance-ui-kit-lessons/01-not-buttons.png)

## 一、它長什麼樣子

一張表單，交給套件的是五份資料：

| 資料 | 內容 |
|---|---|
| 欄位 | 每一格的型別（文字、數字、下拉、單選、地址、電話…）、必填、停用、預設值 |
| 排版 | 卡片、欄數、頁籤、可重複的項目（例如「新增一位受益人」） |
| 規則用法 | 這張表單用了哪些規則、參數是什麼、綁在哪個欄位、什麼時機觸發 |
| 規則定義 | 共用的規則本體：條件、成立時做什麼、不成立時做什麼 |
| 文字資源 | 所有標題、選項、提示、錯誤訊息 |

套件吃這五份，畫面、連動、檢核就出來了。前端寫的 Vue 元件很少，寫的大多是 JSON。

這跟上一篇〈[第一次做人壽專案：我寫的不是畫面，是設定檔](/blog/2026-10-27-config-driven-forms-life-insurance/)〉講的是同一件事，不過那篇是從「使用者」角度，這篇想從「如果要我設計一套這樣的 Kit」的角度看。

---

## 二、八個心法

### 1. 先定資料契約，再做元件

一般的 UI Kit 從元件開始：先做 Button，再做 Input。這個套件的起點顯然是資料格式：一個欄位要有哪些屬性、規則長什麼樣子、文字怎麼引用。元件只是「把這份契約畫出來」的實作。

這在保險業很合理。同一份契約可以給 Web 用、給 App 用、給後端拿去做送件前的檢核，甚至給 PDF 套印用。元件換了、框架換了，契約還在。

國外做壽險投保流程的團隊也有類似的結論：Breathe Life 分享他們的投保表單時，講的就是「設定驅動優於元件驅動」，用 JSON 描述表單，少數幾個欄位元件就能組出很多變化。代價是設定會變得很大，所以他們把設定分成「區段、子區段、題目、欄位」四層，顯示和停用規則可以掛在任何一層。

**心法：Kit 的第一個產出是 schema，不是 Button。**

### 2. 文字一律資源化，選項一律代碼化

在這個套件裡，欄位標題不寫中文，寫 `@ResourceText.某個代碼`；選項不寫陣列，寫 `@ResourceOption.某個代碼`；錯誤訊息用 `getMessage(訊息代碼)` 取。

一開始覺得很囉嗦，後來懂了：

- 保險文件的字是有法律意義的。同一句告知事項，十張表單要一字不差，資源化之後改一個地方就好。
- 選項存的是代碼（例如 `1`、`2`），不是畫面上的字。後端、核保、報表都看代碼，畫面上的字可以改，資料不會亂。
- 需求文件裡的訊息本來就有編號（像「訊息設定 A153」），資源代碼可以直接對回去。

我踩過一個坑：欄位的後綴文字（像「年」「%」）套件不會去解析資源代碼，畫面直接顯示代碼本身。這種「哪些屬性支援資源、哪些不支援」的邊界，就是 Kit 要寫清楚的地方。

**心法：畫面上每一個字都要有出處，每一個選項都要有代碼。**

### 3. 規則是資料，不是程式

規則在這個套件裡長這樣（示意）：

```json
{
  "ruleKey": "Validate_FieldValue_NotZero",
  "declare": { "@Field": "", "$Zero": "0" },
  "conditions": ["@Field == $Zero"],
  "then": ["error @Field = getMessage(EM_NOT_ZERO)"],
  "else": ["clearError @Field"]
}
```

規則定義是共用的，每張表單只寫「用法」：這條規則套在哪個欄位、參數填什麼。同一條「不得為 0」可以套在十幾個欄位上，不用寫十幾次。

好處是**每一條規則都能對回需求文件的一列**。人壽的需求文件動輒幾百列檢核與連動，我的受益人表單光身故頁籤就兩百多列。規則寫成資料之後，可以逐列標註：已完成、重用哪條、等哪個 API、為什麼不做。這份對照表本身就是交付物。

上面查到的保險表單引擎文章也提到，保險的表單是「受監理的文件」，版本、變更紀錄、誰改了什麼都要查得到。規則寫在資料裡，比寫在程式碼裡容易查得多。

**心法：規則要能被列出來、被計數、被追溯，所以它得是資料。**

### 4. 命名規範要能被機器檢查

專案裡的規則名稱有固定格式，大概是 `<Validate|Interact>_<對象>_<效果>`，而且有一支腳本會檢查。條件裡不准出現方括號和單引號；舊的不合規名稱放在一份「基準清單」裡，**這份清單只能減少，不能增加**。

這招我很喜歡。命名規範寫在文件裡，三個月後一定會走樣；寫成檢查腳本加上只減不增的基準，新程式碼一定合規，舊的慢慢還債。

**心法：規範只要靠人記，就一定會壞；能寫成檢查的，就寫成檢查。**

### 5. 擴充點要明確，而且要有門檻

DSL 再強也有寫不出來的東西。例如「同一順位的受益人比例加總要等於 100」「卡片之間證號不可重複」，這種要跨很多筆資料計算的規則，用條件式寫不出來。

套件留了一個擴充點：用裝飾器註冊自訂的規則執行器。執行器負責算，算完把結果交回給規則定義的條件和動作。所以畫面上的錯誤顯示、清除，還是走套件的那一套，行為一致。

但團隊對擴充點有門檻：

- **業務規則**做不到，可以寫執行器。
- **畫面能力**做不到（例如選項要靠左、頁籤裡要放新增按鈕），不准自己寫 CSS 覆寫或自製元件，記下來等套件補。

一開始我覺得後者太保守。後來想通：每個專案自己補 CSS，套件升級時全部會壞；把缺口回報給套件，下一版大家一起受惠。

**心法：擴充點開給「規則」，不開給「外觀」。**

### 6. 做不到的事，寫成有編號的限制

專案有一份 issues 文件，每個套件限制都有編號（`KIT-001`、`KIT-002`…），內容固定是三段：

1. **現象**：哪個屬性、在什麼情況下不支援。
2. **暫行做法**：現在怎麼繞過（例如後綴改寫直接文字）。
3. **關閉條件**：套件做到什麼，這個暫行就可以拿掉。

這讓「Kit 不夠用」從抱怨變成可以排程的工作。對做 Kit 的人來說，這份清單就是下一版的需求。

**心法：Kit 的缺口要被記錄成 backlog，而不是被各專案默默繞掉。**

### 7. 重複項目是最難的那塊

保險表單最麻煩的不是單一欄位，是「可以新增好幾筆」的東西：受益人、附約、眷屬、告知事項明細。

套件有一種可重複的元件，每一筆的欄位會綁成 `清單[索引].欄位`。難的是規則：同一條規則要「只檢查被改的那一筆」，整表檢核時又要「每一筆都檢查」，錯誤要顯示在對的那一張卡片上。還有一類規則是「筆跟筆之間」的：證號不可重複、同順位比例加總、只能有一位法定繼承人。

這塊我寫了兩個執行器才補起來。如果我來設計 Kit，重複項目的規則綁定會是第一優先要想清楚的地方，因為壽險的表單幾乎每一張都有。

**心法：壽險 Kit 的難度不在欄位，在「一對多」。**

### 8. 用真的 renderer 測試，用設定檢查設定

套件是用 tgz 檔版本化發佈的，專案鎖定在某一版。這兩週就遇過一次套件更新，型別和元件都有變動。

所以測試很重要。專案的測試不是測 JSON 長怎樣，而是**把設定交給真的表單元件掛起來**，模擬點選、輸入，檢查欄位有沒有停用、錯誤有沒有出現。另外有一層「設定檢查」：每個資源代碼都要找得到、每個規則用法都要有對應的定義、綁定的欄位都要存在。

我在這裡學到一課：設定裡有寫、規則有綁，都不代表使用者看得到。有一次兩個欄位的檢核就是不會跳，查了才知道那兩格預設停用，套件不檢核停用的欄位。只有掛真的 renderer 才測得出來。

**心法：Kit 的測試要測「畫面上看到什麼」，不是「JSON 寫了什麼」。**

## 三、回頭看那個職缺

如果現在再去面試那個「做 UI Kit」的職缺，我大概會這樣回答：

保險公司的 UI Kit，元件只占三成。另外七成是：

1. 一份穩定、能跨端共用的**資料契約**
2. 一個能把需求文件逐列落地的**規則引擎**
3. 一套**文字與代碼**的資源管理
4. 有門檻的**擴充點**和有編號的**限制清單**
5. 能被機器檢查的**命名規範**和掛真畫面的**測試**

外觀當然重要，但在這個產業，**正確、一致、可追溯**排在好看前面。

我那時候沒上，現在每天在用別人做好的 Kit，從使用端把這些心法一條一條撞出來。也算是用另一種方式補完那場面試。
