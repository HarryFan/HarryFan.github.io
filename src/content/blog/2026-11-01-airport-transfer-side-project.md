> 這是我自己練習用的 side project，不是幫案主交付的成品。文中的店家、乘客、司機、價格都是假資料，費率是我自己假設的示範值。

最近在找接案，看到一則發案：一間做機場接送的小車行，想要一個「線上預約單＋店家後台」，預算兩萬。

兩萬塊做一個前後台，老實說很緊。但我發現這個案子很適合拿來練一件我一直想補的能力：**把一則幾行字的發案，變成可以動手寫程式的規格。**

做完之後我的結論是：**寫程式只佔一半。另一半是搞清楚要做什麼、哪些規則還不能確定、哪些決定以後會後悔。** 這篇記錄我怎麼走完這一輪。

---

## 從一則發案開始

發案內容大概就幾行：乘客可以線上預約接送機，店家後台可以看預約、確認、派車，之後最好能把 Messenger、LINE 的訊息集中在一起。

看起來很清楚，但真的要開始寫，馬上卡住：

- 一台轎車可以坐幾個人、放幾件行李？
- 最晚要提前多久預約？
- 接機的時間要算航班落地，還是落地後再等一下？
- 價格是固定價，還是店家確認時可以改？
- 半夜的班要不要加價？

這些都不是工程師能自己決定的事。所以我做的第一件事不是開專案，而是**列一份要問案主的問題清單**，總共十五題。每一題後面都寫上「目前先假設什麼」，例如轎車先假設 4 人 3 件行李、最晚提前 3 小時、23:00 到 06:00 加價 200 元。

這樣做有兩個好處。一是我可以先往下做，不用等案主回覆；二是哪天案主回答了，我知道要改的是哪一條規則，不會整包重來。

## 先切範圍：兩萬塊做不完全部

「Messenger、LINE 統一收件匣」這個需求，光串兩家平台的 API 就不只兩萬。

所以我把需求拆成兩期：第一期只做預約單和店家後台，第二期才做訊息整合。然後把每個功能寫成有編號的使用者故事，乘客端是 BK-01 到 BK-05，店家端是 BO-01 到 BO-07。

編號看起來很像大公司在搞流程，但對一個人接案其實很好用。跟案主討論時可以說「BK-04 報價明細那條」，寫測試時也用同一個編號，之後看到某個測試失敗，馬上知道是哪一條需求壞了。

## 規格先行：一份 API 合約，前後端都照它

功能定下來之後，我先寫 OpenAPI 合約，才寫程式。

前端的 TypeScript 型別直接從這份合約產生，後端照著合約實作。這樣前後端對 API 的理解只有一份，不會出現「後端回傳 `price`，前端在讀 `amount`」這種事。

這件事我寫成了一份架構決策紀錄（ADR）。整個專案寫了五份，每份都是同一個格式：當時的背景、做了什麼決定、要付出什麼代價、還考慮過哪些做法。寫 ADR 最大的收穫不是給別人看，是逼自己講清楚「為什麼不選另一個」。

## 業務規則放在哪裡

這是我在這個專案最想練的部分。

接送預約的規則其實不少：人數和行李不能超過車型上限、接機一定要填航班編號、用車時間至少要三小時後、只有「已確認」的預約才能派車、已完成的不能取消。

這些規則我全部放在後端一個叫 `Reservation`（預約）的類別裡，而不是散在 Controller、Service、前端表單裡。預約的狀態只能從「待確認」走到「已確認」、「已派車」、「已完成」，或中途「取消」，跳過任何一步，它自己就會拒絕。

後端用六角架構切層：領域層和應用層是純 Java，完全不知道 Spring 的存在，Spring 只負責在最外層把東西組起來。我還加了 ArchUnit 測試，如果哪天有人在領域層 import 了 Spring，測試直接紅燈。

其中一個讓我想比較久的決定是**報價要不要存起來**。

最直覺的做法是只存總價，明細要看的時候再用費率表算一次。但費率表一定會調整，一調整，上個月的預約打開來，明細就跟當初報給客人的不一樣了。客人來問的時候，店家會說不清楚。

所以我決定在建立預約的當下，把報價和每一行明細存成一份快照，跟著預約走。代價是報價那邊和預約這邊各有一份長得很像的類別，但這是刻意的：兩邊改動的理由不一樣。

## 用中文寫測試情境

驗收測試我用 Cucumber，而且直接寫中文：

```gherkin
@BK-04
場景: 夜間用車會加價
  假設 用車時間改成 "2026-11-02 05:30"
  當 乘客用 轎車 送出預約，乘客 2 位、行李 2 件
  那麼 參考報價是 1500 元
```

這段是可以跑的測試，也是可以直接貼給案主看的規格。案主不用懂程式，看得懂「凌晨五點半用車會加價、總共 1500 元」對不對就好。

需要時間的情境，我做了一個可以手動往前撥的時鐘，例如「現在是 10:00，有人想預約 12:00 的車」，不用真的等時間過去。

單元測試則是照 TDD 的節奏：先寫一個會失敗的測試，確認它真的是紅的，再寫剛好讓它變綠的程式。前端的 Vitest 現在是 51 個測試。

## 這輪做完，我學到的

**需求分析的產出，是一份問題清單。** 不是一份完美的規格。能寫出「這裡我不知道，我先假設 X」，比假裝什麼都懂有用得多。

**範圍是談出來的。** 兩萬塊不是不能做，是不能全做。把需求切成兩期、講清楚每一期做什麼，案主才有辦法做決定。

**架構決策要寫下來。** 報價存快照、操作紀錄跟領域事件分開、規格先行，這些當下覺得理所當然的決定，三個月後一定忘記為什麼。ADR 就是寫給未來的自己。

**規則放在一個地方。** 業務規則集中在領域模型裡，前端只是幫忙提早擋，後端才是最後一道關。案主改規則的時候，我知道要去哪裡改。
