Maple Kuo 每次買鹹酥雞，都會先在心裡算一次自己點了多少錢。嫌每次都要算，他乾脆請 Claude 做一個點餐計算機。品項按一按，總價就出來了，還可以和店家結帳的金額對一下。

我在 GatherConf 2026 聽他講〈那些跟 Claude Code 有關的兩三事〉時，覺得這個開場很好懂。做一個自己用的小工具，在聊天介面就能開始。等到要改的是一個已有十幾年的專案，事情就變了。你要先知道既有元件在哪裡、這次改動會碰到哪些使用者行為、測試過了到底代表什麼。他後半場示範的，就是他每天怎麼把這些問題交給 Claude Code 處理。

## 聊天和改專案，差在模型手上有哪些工具

Maple 把 AI Agent 拆成「大腦加工具」。大腦是語言模型，他用「今天天氣」請台下接下一句，說明模型如何根據前面的內容預測接下來的文字。至於查天氣，模型可以提出要呼叫哪個工具，真正送出查詢、把結果取回來的是外部程式，模型再根據回傳內容整理回答。

換到程式開發也是一樣。要回答「這個專案的登入怎麼做」，Claude Code 可以先搜尋程式碼，再讀相關檔案。要實作功能，它手上也有改檔、執行指令和跑測試的工具。Maple 談 Claude Code 的價值時，接著就從這裡往下講。除了用現成工具，他也會把自己的開發流程寫成 Skill，或把任務交給子代理（Subagent）處理。

## 聊天畫面只多一句，模型收到的脈絡可能多很多

他接著拿鹹酥雞計算機示範。第一輪請 Claude 做計算機，第二輪只說把按鈕改成藍色。畫面上看起來多了一句話，模型需要的卻包括前面交代的需求、自己的回覆，以及這一輪的修改。前面如果已經有錯誤假設，也可能被一起帶到下一輪。

這裡有兩個容易混在一起的功能。

- **提示詞快取**（Prompt Caching）會重用符合條件的既有前綴。前段內容保持一致，就有機會減少重複處理。Maple 用這點解釋，為什麼長對話接著聊，有時比表面上看起來多耗額度。實際用量還會受快取是否命中等因素影響。[Anthropic 的提示詞快取文件](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
- **對話壓縮**（`/compact`）會把舊對話摘要成較短的內容，騰出上下文空間。Maple 提醒，摘要有取捨。已定案的需求、例外條件和驗收方式，值得寫進專案文件，後面才有地方回查。[Claude Code 指令文件](https://code.claude.com/docs/en/commands)

他也講到，一個 Skill 可以先用 `SKILL.md` 保存操作步驟，有需要再帶入參考資料。以他的用法，有些任務可以在主對話進行，有些適合用 `context: fork` 交到獨立的上下文。譬如只是想知道登入機制，子代理可以讀一批檔案，最後回傳結論和相關路徑。主對話不用一路帶著每份檔案的中間輸出。另開一個子代理同樣有用量成本，他會看這個任務是否值得獨立做。[Claude Code Skills 文件](https://code.claude.com/docs/en/skills)

## 兩個 Skill 問清楚，三個子代理分開做

Maple 每天用的流程，先用 `/pm` 和 `/arch` 做出兩份文件，再把工作交給不同角色。台上的流程圖最後還有 QA，會把應用程式跑起來做 API 測試。

| 步驟 | Maple 怎麼分工 |
| --- | --- |
| `/pm` 釐清需求 | 先問為什麼要做這個功能、使用者會怎麼操作、狀態怎麼變，以及怎樣算驗收通過。把答案寫成接下來共用的需求文件。 |
| `/arch` 盤點實作 | 讀需求和現有程式碼，找出能沿用的元件、工具與做法，再想好怎麼測，整理成實作計畫。 |
| Implementer 實作 | 依照計畫修改，沿用專案的寫法。命名要讀得懂，已經有合用的工具就直接用。兩段程式碼長得像，也得先看業務規則是否真的相同，再決定要不要抽成共用邏輯。 |
| Reviewer 看程式碼 | 檢查實作有沒有過度抽象、是否符合既有風格，或是用新路徑繞過原本封裝好的流程。 |
| Test Reviewer 看測試 | 確認測試有守住使用者行為，並檢查有沒有為了讓測試通過，就去改掉原本的驗收條件。 |
| QA 跑應用程式 | 啟動應用程式做 API 測試。實作後的審查可以再跑幾輪，依發現的問題修正。 |

我最記得的是他怎麼看測試。他會問，把這支測試刪掉之後，我們失去哪個原本保護的行為？以我做 Vue 表單的經驗來說，如果測試只驗證「送出函式有被呼叫」，就看不出欄位驗證失敗時，畫面有沒有顯示錯誤、把焦點帶回第一個有問題的欄位。這些行為要先寫進需求，Test Reviewer 才知道要檢查什麼。

## 規格太長看不下去，就讓 AI 先問你

Maple 說，他這套做法是從規格驅動開發（SDD）延伸出來的。但連他自己也遇過一個問題。每次都要讀兩份文件，讀久了只想按「OK，你挑最適合的方案做」。人沒有參與幾個重要決定，文件再長，AI 還是得自己猜。

他的做法是讓 AI 先讀文件，再把模糊的地方拆成一題一題來問。以需求文件來說，他希望問題能落在真實使用情境。譬如「使用者關掉編輯視窗時，尚未儲存的內容要保留嗎？」這種問題有明確的行為可以決定。問完再請 AI 重述需求和驗收方式，確認雙方對同一件事的理解一致。實作途中發現原先的方案走不通，仍然可以回去改文件和計畫。

這點我很有感。做久了前端，有些決定我會習慣放在腦中，像是關閉視窗後要不要保留輸入、共用元件哪裡有其他頁面在用。直接交辦給 AI，它就會用手上看得到的資料推一個答案。先把真正會影響使用者的問題問出來，再把這些答案交給實作和測試的人，比事後從一大份程式碼裡找出哪裡猜錯容易得多。

Maple 最後用七十分到九十分形容他在工作上的感受。流程和工具能讓初稿更接近可用，剩下那段要靠人理解舊系統、讀改動、補測試，以及判斷產品成品能不能交付。我聽完最想帶回去的，是下次安排 Claude Code 做功能時，先讓它問出我還沒寫下來的驗收條件，再請另一個角色檢查測試有沒有真的守住那些條件。
