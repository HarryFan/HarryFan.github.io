「後台要能匯出訂單。」

這句話看起來很清楚。前端可以開始畫按鈕，後端可以開始寫 API，AI 也能很快生出一個下載 CSV 的功能。

但接著就會遇到問題：誰可以匯出？匯出目前這一頁，還是符合篩選條件的全部資料？沒有訂單時要怎麼辦？收件人的電話能不能放進去？十萬筆資料要等多久？

如果答案都留到實作時才決定，每個人就會各自補一份理解。

**SRS 的用途，就是把這些需要共同確認的答案寫下來，成為開發、測試與驗收的共同基準。**

## SRS 是什麼

SRS 是 **Software Requirements Specification，軟體需求規格書**。

它描述軟體必須提供哪些行為、達到哪些品質要求，以及受到哪些限制。讀者不只工程師，也包括產品負責人、系統分析師、測試人員、維運與業務領域的利害關係人。

NASA 的軟體工程手冊將 SRS 視為後續設計、實作與測試的重要依據，也會透過資料字典、介面文件補足細節。換句話說，需求可以分在幾份互相連結的文件裡，重點是找得到、對得起來。[來源：NASA 的 SRS 說明](https://swehb.nasa.gov/spaces/SWEHBVB/pages/32604425/SRS%2B-%2BSoftware%2BRequirements%2BSpecification)

如果要找正式的需求工程標準，可以從 [ISO/IEC/IEEE 29148:2018](https://www.iso.org/standard/72089.html) 開始。它涵蓋需求工程流程、產出資訊與文件內容；本文下面的範本則是便於小型專案使用的整理，並非逐條重現標準格式。

## PRD、User Story、SRS，各自在回答什麼

上一篇[彩虹小聚的分享](/blog/2026-11-24-wordpress-rainbow-meetup-tree-god-ai-game/)談到，先把 User Story、PRD 和專案約定寫好，再讓 AI 開工。加上 SRS 之後，可以用下面這張表理解各自的重點。

| 文件或工具 | 主要回答的問題 | 以訂單匯出為例 |
|---|---|---|
| PRD，產品需求文件 | 為誰解決什麼問題？範圍與優先順序是什麼？ | 讓出貨人員取得待出貨清單，第一版先支援 CSV |
| User Story，使用者故事 | 哪個角色想做什麼，為了什麼目的？ | 身為出貨人員，我想匯出待出貨訂單，以便安排當日出貨 |
| SRS，軟體需求規格書 | 在哪些條件下，系統必須做出什麼行為？ | 驗證匯出權限、套用篩選條件、限制欄位與筆數、處理失敗 |
| 技術設計文件 | 系統內部如何完成這些要求？ | API 如何拆分、資料怎麼查、是否採用背景工作 |
| 驗收案例 | 用什麼情境與結果確認要求已做到？ | 無權限的帳號呼叫匯出介面，必須遭拒且拿不到訂單資料 |

這是常見的工作分工，不是每間公司的固定命名。有些團隊的 PRD 已經包含詳細規則與驗收條件，有些團隊則把內容拆進需求管理工具。Atlassian 的 PRD 指引也包含目的、功能、行為與成功標準，和 SRS 的內容可能重疊。[來源：Atlassian 的 PRD 指引](https://www.atlassian.com/agile/product-management/requirements)

**先確認團隊缺的是哪一層資訊，再決定要不要多一份文件。** 同一條規則複製到三個地方，之後卻只更新其中一份，反而更容易出錯。

## 一份 SRS 要寫到哪些事

可以先把內容分成五個部分。

### 1. 目標、範圍與名詞

說明系統服務誰、這一版包含哪些功能、哪些事情留待之後處理。重要名詞也要先對齊。

例如「有效訂單」是已付款，還是未取消？「一天」以哪個時區計算？不同人如果給出不同答案，後面的表格寫得再細，也會建立在不同前提上。

### 2. 功能性需求：系統要做什麼

描述可以觀察到的行為，例如登入、查詢、匯出、通知與權限檢查。每個重要流程都要考慮輸入、前提、輸出與例外。

對前端來說，這會直接影響畫面：資料載入中要顯示什麼、查無結果怎麼呈現、權限被收回後如何回應、失敗時能不能重試。只有一張成功畫面的設計稿，還不足以回答這些問題。

### 3. 非功能性需求：要達到什麼品質

例如效能、可用性、可靠性、可維護性與易用性。這些要求需要可檢查的條件。

「查詢要很快」還不能驗收。要補上測量環境、資料量、負載、時間門檻，以及測量的起點與終點。平均一秒，也可能代表少數使用者每次都等十秒，必要時要指定百分位數。

安全要求也要拆開看。「只允許特定角色匯出」本身是系統行為，可以列成功能需求；整體安全目標則可能橫跨多項功能與品質要求。分類是為了方便管理，不必硬把所有安全規則塞進同一欄。

### 4. 資料與外部介面

有哪些輸入欄位？必填還是選填？金額單位是元還是分？時間格式與時區如何處理？外部服務失敗時，系統應該回報什麼？

NASA 的 SRS 指引也把外部介面列為需求的一部分，涵蓋軟體和其他系統、使用者等對象之間的輸入、輸出與互動規則。[來源：NASA 的外部介面需求說明](https://swehb.nasa.gov/spaces/SWEHBVD/pages/140640605/SRS%2B-%2BSoftware%2BRequirements%2BSpecification)

實際專案可以連到 API 契約或資料字典，並標明適用版本。

### 5. 限制、假設與待確認事項

例如必須沿用既有登入服務、需要支援哪些瀏覽器，或依賴另一個系統提供資料。這些條件會影響可行性與估時。

已經確認的限制，和暫時拿來推進討論的假設，要分開標示。還沒決定的事情則寫進待確認清單，附上負責人與確認期限。不能因為文件需要填滿，就替業務做決定。

## 把「可以匯出訂單」拆成可驗收需求

下面是一個**虛構的教學案例**，不是現成產品規格；欄位、筆數與效能門檻都需要依專案重新確認。

假設第一版的目標是：出貨人員能取得目前篩選條件下的出貨清單，最多一次匯出一千筆。

| 編號 | 需求 |
|---|---|
| FR-EXP-01 | 系統必須在每次匯出請求時，由伺服器驗證登入狀態與 `order:export` 權限。未通過者不得取得訂單資料。 |
| FR-EXP-02 | 系統必須匯出同時符合請求篩選條件與使用者資料存取範圍的全部訂單，不受列表目前頁碼影響。 |
| FR-EXP-03 | 匯出檔必須使用 UTF-8 CSV，欄位依序為訂單編號、商品名稱、數量與出貨狀態。檔案不得包含其他欄位。 |
| FR-EXP-04 | 查無符合資料時，系統必須顯示「沒有可匯出的訂單」，且不產生下載檔。 |
| FR-EXP-05 | 符合資料超過一千筆時，系統必須拒絕匯出，提示「請縮小篩選範圍」，且不產生部分資料的檔案。 |
| FR-EXP-06 | 匯出失敗時，系統必須顯示「匯出失敗，請稍後再試」，並保留使用者原有的篩選條件。 |

這還不是完整 SRS。例如一張訂單有多個商品時要拆成幾列、查詢到下載之間有人改單怎麼處理，都還需要討論。**把缺口列出來，也是寫規格的成果。**

效能需求可以另外寫成：

> <strong>NFR-EXP-01：</strong>在雙方確認的測試環境與十萬筆訂單資料集下，以二十個並行使用者連續測試十分鐘，每次匯出一千筆；從伺服器接到請求到輸出完整回應的時間，P95 必須不超過三秒，匯出錯誤率不超過 1%。此測量不包含使用者端的網路傳輸時間。

測試環境的硬體、資料分布與設定，還要記在附件裡。這樣下一次換環境測量時，才知道結果能不能比較。前端點擊到檔案下載完成的體感時間，則可以再訂一條獨立要求。

## 需求、設計與驗收要接得起來

「匯出完成前，畫面要顯示處理中」是一項行為要求。「用哪個狀態管理套件」則通常是實作選擇。除非沿用某項技術已經是確認過的限制，否則可以留在設計階段評估。

NASA 的需求撰寫檢查表強調清楚、可驗證、用語一致與可追溯，也提醒需求應盡量描述需要的結果，避免太早綁定實作。[來源：NASA 的需求撰寫檢查表](https://www.nasa.gov/reference/appendix-c-how-to-write-a-good-requirement/)

回到匯出案例，可以把 FR-EXP-05 寫成這樣的驗收情境：

```gherkin
Scenario: 符合資料超過匯出上限
  Given 使用者已登入且具有訂單匯出權限
  And 使用者有權存取且符合目前篩選條件的訂單共 1001 筆
  When 使用者要求匯出訂單
  Then 系統顯示「請縮小篩選範圍」
  And 系統不產生下載檔
```

Given／When／Then 分別描述前提、事件與預期結果，是 Gherkin 的情境寫法。它可以幫助討論，但貼進文件本身不代表測試已自動化，仍需要實作對應測試。[來源：Cucumber 的 Gherkin 文件](https://cucumber.io/docs/gherkin/reference/)

再加一張小小的追溯表，規格就比較不容易變成孤島：

| 使用者需求 | 規格編號 | 驗證方式 |
|---|---|---|
| 出貨人員取得正確的出貨清單 | FR-EXP-02、03 | 篩選與資料範圍測試、CSV 欄位與內容比對 |
| 大量資料時能理解匯出限制 | FR-EXP-05 | 分別測試 1000 筆可匯出、1001 筆遭拒 |
| 無權限者無法取得資料 | FR-EXP-01 | 直接呼叫 API，檢查拒絕結果與回應內容 |
| 在約定時間內完成匯出 | NFR-EXP-01 | 固定環境下的負載測試 |

如果上限改成五千筆，就能沿著編號找到需求、錯誤提示、邊界測試與效能假設，逐一檢查。

## 小型專案可以從這份範本開始

不用一開始就寫成幾十頁。可以先挑一個功能，用 Markdown 記下能支持討論與實作的資訊：

```markdown
# 訂單匯出 SRS

## 文件狀態
- 版本：0.1
- 狀態：待確認
- 需求負責人：
- 共同審查：產品／業務、開發、測試

## 目標與範圍
- 解決什麼問題、提供給誰：
- 本次包含：
- 本次不包含：
- 名詞定義：

## 功能需求
### FR-EXP-01
- 需求來源與理由：
- 前提與觸發條件：
- 系統必須提供的行為：
- 失敗或例外情境：
- 驗收方式：
- 優先順序：

## 品質要求
- 效能、可靠性、安全性、易用性等目標：
- 測量條件、門檻與驗證方式：

## 資料、介面與限制
- 資料字典／API 契約連結及版本：
- 外部依賴與相容性限制：
- 已確認假設：

## 待確認事項
| 問題 | 影響 | 負責人 | 確認期限 |
|---|---|---|---|

## 變更紀錄與追溯
- 修改日期、原因、受影響需求與測試：
- 確認人與確認結果：
```

寫完後，請業務或產品確認「這是不是要的行為」，請工程師確認可行性，再請測試人員檢查能不能驗證。需求定版後仍然可以修改，只是改動要有紀錄，相關設計與測試也要跟著更新。

## AI 可以幫忙整理，未決問題要留給人確認

在 AI 協作開發裡，SRS 很適合拿來固定上下文。比起只說「幫我做訂單匯出」，給它已確認的角色、資料範圍、錯誤處理與驗收方式，能減少需要自行猜測的地方。

我會這樣下提示：

```text
請根據以下訪談筆記整理 SRS 草稿。

1. 區分已確認需求、假設與待確認問題。
2. 每條需求加上唯一編號，標出對應的筆記段落。
3. 檢查權限、資料範圍、狀態變化與失敗情境是否有缺漏。
4. 提議驗收案例；尚未確認的效能數字、保存期限與權限規則，
   請列成問題，不要自行補成已確認需求。
5. 找出互相矛盾或無法驗證的敘述，說明需要誰做決定。
```

後續讓 AI 寫程式時，再指定這次要實作哪些需求編號，完成後列出對應的程式與測試。這份對照仍然要由人審查，才能確認它真的符合需求。

下一次收到「加一個匯出按鈕」時，可以先問三件事：**誰能用、哪些情況會失敗、怎樣算完成。** 把答案記下來，再讓需要參與的人一起確認，就是一份有用的 SRS 的起點。
