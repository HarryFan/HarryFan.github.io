Eva Chu 在等 AI Agent 跑完一項工作時，看見先前做的介面還有問題。她順手把要改的地方打在輸入框裡，還沒按送出。照她在台上的回憶，Agent 跑完原本的任務後回報，連輸入框裡那項也一起改了。

有人幫忙順手修好，當下當然省事。可是換成寄信給客戶、更新資料庫，或是刪掉一筆還有人在用的資料，這種「順手」就會讓人想問：**我還沒交辦的事，為什麼已經做了？**

這是我在 GatherConf 2026 聽 Eva 講 Google Antigravity 時，最有印象的一段。她的題目是〈從 Vibe Coding 踩坑到培養共創默契：我用 Antigravity 打造產品的 UX、Agentic UX 與 AX 實戰〉。整場講的是她用 AI 開發自己的 Side Project，遇到哪些麻煩，又怎麼把每次要盯著 AI 做的事，慢慢變成專案裡可重複執行的流程。

## 專案做大後，最累的是一直重講和重查

Eva 一開始遇到的狀況，做過前端的人應該很熟。畫面看起來有了，串進來的資料卻要自己查才知道對不對。資料、邏輯和介面攪在一起，改了 A 會壞 B，回頭修 B，A 又出問題。她還碰過 Agent 回報某項功能已經完成，追問到底改在哪裡，它才承認還沒做完。

長對話也增加了麻煩。Eva 提到，脈絡在執行中被壓縮後，她看過 Agent 在一個迴圈裡跑了約十分鐘，問題還是沒解。她也碰過另一種情況，Agent 還記得自己有任務，卻很快就回報完成。對她來說，這兩種情況都得回到專案裡看實際成果，光看回覆很難判斷做到哪了。

另外還有清資料的成本。外部抓回來的資料有雜訊，開發過程中也會留下用不到的程式碼和舊資料。Eva 會請 Agent 先列出疑似用不到的項目，因為殘留的東西有時又被拿去當作下一次修改的依據。她說，光清這批資料就花了大約三個禮拜。

## 什麼時候讓 Agent 繼續，什麼時候先等我看過？

Eva 用「單向門」與「雙向門」來說明。改個顏色，跑完覺得不對再改回來，通常是雙向門。信一旦寄給客戶，對方可能已經收到，這就是單向門。Agent 可以先擬信，但應該等人確認後才送出。

她也把執行拆成內外兩層。**Inner Loop** 是 Agent 自己寫程式、檢查，沒通過就再修。**Outer Loop** 是規模更大的工作流程，例如定期抓外部資料，過濾後產出結果，再交給人看。外層流程跑到哪裡要先停，可以根據風險設定。像樣式微調可以讓它先完成再看，會對外送出或影響資料的動作，就在執行前安排確認。

這兩段也讓我比較懂她在講的 **AX（Agent Experience）** 和 **Agentic UX**。以這場的例子來說，AX 可以從「Agent 接到任務時，看得到哪些規則和資料」來理解。Agentic UX 則可以問「工作開始後，我看不看得到它的進度、能不能暫停、要在哪裡點頭放行」。

## 她怎麼用 AGENTS.md 拆開資料與 UI

Eva 把規則分成兩邊寫。一邊是資料、運算和後端怎麼接，另一邊是畫面、版面和視覺怎麼處理。這樣做的差別，在她示範的兩種任務裡特別清楚。

| 任務 | Eva 的做法 |
| --- | --- |
| 新增頁面 | 先確認資料從哪裡來、要做哪些運算，再安排版面和頁面上要顯示的項目。 |
| 修改現有頁面 | 先判斷這次要改資料邏輯、排版還是文字，再讓 Agent 找對應的規則。 |

她先確定頁面和資料的架構，再處理設計系統。字級、留白等比例，她會請 AI 先提方案，自己看過結果，再把可共用的規則寫下來。同一份資料會出現在多個地方時，她也會要求寫在同一個來源，讓各頁面共用。否則 Agent 在三個地方各寫一次，後面就要查三份內容有沒有對上。

不管換了哪個對話，Agent 都能回到這份檔案找到原本的決定。這就是她說的脈絡工程（Context Engineering）在專案裡的樣子。

我做 Vue 表單時會把這個做法用在任務單。譬如這次只是調整欄位間距，就請 Agent 先找既有的版面規則，另外記下欄位驗證、資料格式和送出邏輯都要照現有規格走。這樣我看改動時，就知道有哪些地方需要特別比對。

## 外部資料先清理，再交給網站使用

Eva 說，她也遇過 Agent 沒先問就改了資料庫，有時甚至刪掉資料。她另一個顧慮是，網站或圖片裡可能夾著指令，Agent 在讀取外部內容時，可能把這些文字當成下一步要做的事。

她在自己的專案裡把流程拆開。先擷取外部資料，再把原始內容送進權限受限的環境清理，接著將處理過的資料存入資料庫，最後才提供給頁面呈現。她口頭用「關在一個小房間」形容清理的階段。我的理解是，這一步只需要足夠的權限完成整理，如果還需要寫入資料庫，就讓另外負責寫入的步驟處理。

## 測試腳本先跑，人再拿起手機操作

Eva 後來在專案裡寫測試腳本，讓 Agent 按規則檢查，遇到沒通過的項目就退回修正，修完再跑一遍。她也會提供幾種使用者角色，描述他們會怎麼使用網站，請 Agent 模擬各自的操作，再把結果交給她檢查。她提到，AI 有時會寫出一般人看不懂的醫療或法律用語，也可能想像出和現實不同的使用情境。這些都需要她回到實際的使用者，確認文字和流程該怎麼改。

Q&A 有人問，工程師是不是也該學設計。Eva 舉了響應式網頁的例子。把桌機瀏覽器縮窄，可以先看版面有沒有跑掉。但她還是會拿 Android 手機或 iPhone 實際操作，因為拉小視窗跟在手機上滑、點、輸入的感覺會有差。

這是我最想帶回工作裡的做法。下次交辦 Vue 表單，我會在規格上先寫出要驗收的動作，例如送出失敗時，畫面要捲到第一個錯誤欄位。Agent 可以先跑測試，最後我會拿手機輸入一遍，看看鍵盤打開時，還能不能看到錯誤訊息和送出按鈕。到這一步，我才知道這張表單能不能交付。
